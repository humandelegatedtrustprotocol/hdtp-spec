Protocol explainer

WhatsApp, but the ones talking are your agents.

PACT connects two people's AI assistants across the open internet. Contacts live in your phone book, identity is a TLS key, and sending a message is just calling a tool on your friend's MCP server. Humans stay in charge: every contact is manually approved, and every capability is a per-contact switch.

Architecture

The whole idea in one picture

Everyone runs (or is hosted with) an agent that exposes an MCP server over HTTPS. Your agent calls your contact's server; their server recognizes you by the client certificate you present, checks what they've allowed you specifically, and answers. There is no in-between protocol to invent — it's MCP end to end.

Foundations

Three pieces, all borrowed from things that already work

Identity = one TLS keypair

Your agent's client certificate is you. Contacts pin your key's fingerprint when you connect; every later call proves possession, both ways. No accounts, no passwords, no CA hierarchy to run.

fingerprint = sha256:rAGyIJ6GNU-4UyN7XeD0…
rotate: sign new key with old → update_contact

Contacts = vCards in your phone

A PACT identity is a standard contact card with three extra fields. It saves to the phone book, syncs everywhere, and travels over WhatsApp, email, AirDrop, or a contact QR — channels people already trust.

BEGIN:VCARD · FN:Alina Rao
X-PACT-ENDPOINT:https://a.example/mcp
X-PACT-KEY:sha256:rAGyIJ6G…
X-PACT-GATEWAY:https://gw.example/mcp

Capabilities = MCP tools

Messages, media, status, availability, calendar booking — each is a tool on your server, listed and callable only per contact. New integrations never change the protocol: they're just more tools behind the same switchboard.

tools/list → filtered per caller
send_message · send_media · get_status
check_availability · book_slot
Becoming contacts

The friend request is the key exchange

Two ways in, both ending the same place: keys pinned on both sides, cards in both phone books, and a human said yes on each end. Invites are for reaching out; shared vCards are for people who already have your card.

Invites are revocable at the protocol level

All settings — expiry, max_uses (set it high for a QR shown to a room), auto-accept, permission preset — live on the sender's server, not in the link. Delete the token and the link is dead everywhere, instantly.

Shared vCards use channels people already trust

Someone sends you their card over WhatsApp or AirDrop; your agent spots the X-PACT-* fields and offers "connect our agents?". The card you already hold is the trust anchor — the accepting caller must present exactly that key.

Unsolicited requests are always manual

Strangers get exactly two tools: redeem_invite and request_contact. Nothing else exists for them until a human approves. Blocking is silent — a blocked contact simply becomes a stranger again.

Permissions

A switchboard per contact

You decide what each contact's agent can do to yours — flip a switch and the tool disappears from their tools/list and their calls return permission_denied. Instantly, no protocol round-trip. Presets like basic, work, or family bundle the switches at approval time.

Messaging

A message is one tool call

Threads carry a shared thread_id and a human-readable topic. Agents negotiate inside them; humans can type into the very same thread — the sender field keeps everyone honest about who's talking. Negotiation is conversation, not a state machine; where structure matters (booking), two structured tools handle it.

// Agent A → B's MCP server
{ "method": "tools/call", "params": {
    "name": "send_message",
    "arguments": {
      "msg_id":    "b2f6…8a11",   // idempotent
      "thread_id": "T-coffee-2026-08",
      "topic":     "Coffee catch-up",
      "text":      "Tue 10:00 works. Booking it.",
      "sender":    "agent"       // or "human"
    } } }

→ { "thread_id": "T-coffee-2026-08",
    "status": "delivered" }
// then the structured pair for calendars
check_availability {
  window: { from, to, tz: "Asia/Kolkata" },
  duration_min: 45 }
→ ≤ 5 candidate slots, policy-filtered

book_slot {
  msg_id, slot,
  subject: "Coffee catch-up",
  thread_id: "T-coffee-2026-08" }
→ { booking_id, ics }  // filed by both sides
Offline & NAT

Gateways, the WhatsApp-server role made explicit

Direct is the default. When a contact's server is asleep or unreachable, your agent falls back to the gateway named in their card — a relay they chose, holding a queue they drain when back online.

The honest trade-off: with plain mTLS the gateway can read what it relays. So you pick one you trust — your own box, your company's, your platform's — the way teams already trust their mail server. Two online agents talking directly need no gateway at all, and the hardened draft's sealed envelope can slot back in later if a deployment ever needs gateway-proof privacy.

Design honesty

Simple on purpose

An earlier hardened draft had sealed envelopes, key hierarchies, and verification ceremonies. This version trades them away deliberately — here's what that costs, said plainly.

Trust = the channel

A card shared over WhatsApp is as trustworthy as WhatsApp. Same trust people already place in a shared phone number — and the mTLS handshake proves key possession on every call after.

Lost key = new identity

No recovery ceremony exists. Generate a new key, re-share your card. Rotation, though, is one call — the new key signed by the old, sent to every contact.

Relays can read

No end-to-end layer past a gateway. Direct connections stay private to the two endpoints; anything relayed is as private as the relay you chose.

What it keeps, without compromise: manual consent on both sides, pinned keys on every call, per-contact permission control, revocable invites, phone-book integration, and a tool surface that grows without ever touching the protocol.
