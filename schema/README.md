# The schema of HDTP's JSON wire objects

`schema/<version>/schema.json` is a JSON Schema (draft 2020-12) of the JSON objects the
specification defines, one file per version directory of `docs/specification/`. The draft's is
generated by `schema/gen.mjs` from the `$defs` of hdtp-identity's `contract/contract.json` — the
contract both of that library's ports are validated against on every gate run — and
`npm run schema:check` fails when it differs from what the contract generates. A released version's
`schema.json` and `reference.md` are frozen at its release: the contract moves on with the library,
and `schema/released.sha256` holds each released file to its bytes, which `npm run schema:check` also
checks. Nothing in them is written by hand.

Beside each schema:

- `reference.md`, the reference page: one section per definition, its members, their types, bounds
  and descriptions. `schema/reference.mjs` generates it from `schema.json` alone (`npm run schema` runs
  it after `schema/gen.mjs`), and `npm run docs:check` fails when the committed page differs.
- `examples/<Definition>/<name>.json`, at least one example of each object below. `npm run docs:check`
  validates every example against its definition, with a control: the same example with one member
  the definition does not list must be refused. The examples were made by real code: the envelope is
  Appendix B's first, the export objects come from hdtp-identity's export writer, and the signing
  request's CSR from its `csr_new`; the certificates and fingerprints are the vectors'.

## What it covers

| Definition | The object | Section |
|---|---|---|
| `Envelope` | a sealed envelope, its four members as a writer produces them | §13.1 |
| `SigningRequest` | a host's signing request, the members of its form | §9.1 |
| `ExportManifest` | an export's `manifest.json` | §9.2 |
| `ContactRow`, `RemovedRow`, `ThreadRow`, `MessageRow` | a row of `contacts.csv`, `removed.csv` and `threads.csv`, and a line of `messages.jsonl`, as JSON | §9.2 |

With them, every definition they reference: `Attachment`, `B64url`, `CertDer`, `Fingerprint`,
`InstantIn`, `Sha256Hex`. The descriptions are the contract's, and speak of "this library" and of
the contract's own sections where the contract does.

## What it leaves out

These are defined by the specification and have no definition in the contract, so a schema of them
would hold to nothing:

- the contact card (§3), which is a vCard, not JSON;
- the protected header of an envelope (§13.1): the contract fixes its members and their order, not
  a schema;
- the invite offer served as `application/hdtp-invite+json` (§4);
- the MCP tools' arguments and results (§6, §7, §8).

## Versions

Until the draft changes the wire, `1.0/` and `draft/` are generated from the same contract and are
the same apart from their `$id` and `title`.
