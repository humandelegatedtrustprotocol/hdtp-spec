# CLAUDE.md — project context for Claude Code

## What this project is

HDTP, the Human Delegated Trust Protocol: person-to-person communication carried out by their AI assistant agents. Each person exposes an MCP server over HTTPS; contacts are mutual, human-approved, and pinned by the fingerprint of the person's root certificate; messages, media, availability checks and calendar booking are permission-gated MCP tools on that server. The specification is the single source of truth: `docs/specification/<X.Y>/` is a released version (an `index.md` and one page per top-level section, in the order the index links them), `docs/specification/draft/` is the next one. `site/spec-source.mjs` is the one reader of that text; every other reader — the whitepaper, the web renderer, the vectors, hdtp-identity's proofs — goes through it.

`explainer/hdtp-explainer.html` is an **Artifact body**, not a standalone page — it starts at `<title>` with no doctype/`<html>`/`<head>`/`<body>` wrapper; never add one. It loads its typefaces from Google Fonts, the one external fetch in this repository. Where the maintainer publishes it is not this repository's concern: do not publish it from here.

## Design north star (decided; a change here is the maintainer's call)

- **Simple over hardened.** Security is mTLS with pinned identities, a narrow sealed envelope (§13: HPKE Base + detached signature under the leaf key), and the smallest key hierarchy there is, in X.509: **the person is a certificate authority** — a self-signed root in the person's wallet is the identity (pinned by its fingerprint), and the host holds a leaf the root issued, naming the endpoint in its SAN and expiring within 398 days (§2, §14). One leaf key does TLS, signatures and sealing. The certificate profile is exact (§14.1: nothing unlisted, strict DER). Post-quantum is deferred, with its path recorded in §13.5; do not reintroduce it piecemeal. There is no log, no sequence number, no relay (§9 is *Hosting*): renewal is a new leaf learned from the chain an envelope carries, "newest `notBefore` wins the instant it is seen" replaces revocation, a move is a new leaf for a new address plus `update_contact` under the receiver's `accept_new_hosts` setting (§5.3), and a host that is left deletes everything. No DIDs, no SAS, no prekeys, no directory, no recovery, no root rotation; a lost or compromised root is a new identity.
- **MCP-native.** Never invent a parallel message protocol; a capability is always an MCP tool behind the per-contact permission switchboard. Auth on this surface is transport-level mTLS, not OAuth.
- **vCard is the contact format.** `X-HDTP-VERSION` (=1), `X-HDTP-CERT` (the leaf certificate, base64url DER — it carries the endpoint, the key, the root's fingerprint as issuer key identifier, and the validity), `X-HDTP-SEAL`. Any other `X-HDTP-*` property is ignored. A card stays under a kilobyte so it fits a QR code; the invite URL carries print; a root is never in a card.
- **Invites are server-side state** (expiry, max_uses, auto_accept, preset, revocation) reachable via a short URL/QR. Nothing sensitive in the URL itself.
- **Honest trade-offs stay documented**: edges see metadata (and read any unsealed traffic); no forward secrecy at the envelope layer; lost root = new identity; card trust = channel trust. Keep these visible in docs and UX copy, never papered over.

## Spec conventions

- The current version is **1.0.0 (2026-10-03)**, in `docs/specification/1.0/`; `draft/` carries `1.1.0-draft`. The envelope header is `v: 1`, HPKE `info` `HDTP-SEAL-v1`, suites `HDTP-SEAL-P256` and `HDTP-SEAL-X25519`; an export's manifest is `hdtp_export: 1`.
- **Versioning (`GOVERNANCE.md`), X.Y.Z:** Z is a correction or clarification that changes no requirement; Y a deliberate release of accumulated work, written in `draft/`; X a wire-breaking generation, the only bump that moves `X-HDTP-VERSION`, `v` and `hdtp_export`. A version being written carries `-draft`. The index page's line `**Version X.Y.Z · date**` is the version and nothing else: the whitepaper cover parses it, the ports' tests hold their `SPEC_VERSION` to its first token, and `vectors/check.mjs` holds `CITATION.cff`, the README's attribution and status lines, `CHANGES.md`'s entry and this file's line above to it. The same check holds every sentence that states a wire version (an envelope's `v`, a card's major, `hdtp_export`, the info label) or says what Appendix B holds to the vectors, the card codec and the schema (`vectors/lib/stated.mjs`): never write such a number without running it, and name no generation by a bare `vN`. What a version changed is in `CHANGES.md`, never in the text. A change to what an implementation must do starts as a SEP (`seps/README.md`).
- Wire-visible changes need a spec edit first, then `npm run vectors` (which splices the JSON into Appendix B of the released version and the draft), then `npm run vectors:check`. When hdtp-identity's contract changes, `npm run schema` regenerates `schema/*/schema.json`; never edit it by hand.
- Tool names snake_case (`send_message`, `redeem_invite`, `book_slot`); permissions dotted (`message.text`, `calendar.book`, `integration.<name>`); errors snake_case codes (`permission_denied`, `invite_invalid` — full list §12).
- Idempotency via caller-supplied `msg_id`; threads via shared `thread_id` + optional `topic`; `sender: agent|human` labeling is mandatory honesty.
- Guest tier (unknown certs) sees exactly `redeem_invite` + `request_contact`, plus the every-tier wrapper `sealed_call` (when sealing is on); `update_contact`, `remove_contact` and `get_card` are always available at contact tier regardless of permissions. A pinned contact calling from a new endpoint is a *new address* (§5.3); a superseded leaf (older `notBefore` than the pinned one) is a guest. Availability responses: ≤5 policy-filtered slots, never raw free/busy.
- The mermaid blocks all live in the specification's pages; keep them syntactically valid when editing — the whitepaper build renders every block and fails on one that does not parse. The explainer's diagrams are hand-authored inline SVG — this rule does not reach them.
- **The name guard.** `scripts/check-names.mjs`, run by `npm run vectors:check`, fails on any tracked path or text carrying a name `scripts/hdtp-names.txt` forbids: the old name in the three spellings its `name` lines give (lower-case, capitalised, upper-case), anywhere except right after `im` or `com`, and the names of behaviours HDTP does not have (key rotation, the relay role, contact sync, coexistence knobs). The list's `once` entry is the one sentence allowed to say what HDTP was called, in `docs/specification/1.0/index.md`. Its `frozen` lines name another repository's manifest of dated records (`<sha256>  <path>` per line), which the guard leaves unread, text and path, while each file is the bytes its line names; this repository has none. Both files are the canonical copies: every other HDTP repository's gate runs byte-identical copies and compares them with these.

## Working preferences

Minimalistic, precise code that fits the module it lands in; read existing code first; no speculative features; stick to the objective. Prefer prose + small tables in docs over bullet sprawl.

There are two builds, sharing one markdown pipeline (`site/markdown.mjs`) and one mermaid pipeline (`site/mermaid.mjs`: the bundled mermaid from `node_modules` inside headless Chrome, flowcharts and state diagrams laid out by ELK, nothing fetched at render time). The whitepaper: `npm run build` (`site/build-whitepaper.mjs`) renders the newest released version into `dist/hdtp-whitepaper.pdf`, and is a gate too — it fails on a heading over 120 characters, on a mermaid block that does not render, and on a PDF that does not carry its licence, which it reads back (`site/pdf.mjs`). The web fragments: `node site/spec-html.mjs --ref <ref> --out <dir> [--version <X.Y>|draft]` renders one *committed* version into what the protocol site vendors (`spec.html`, `diagrams.json`, `toc.json`, `musts.json`, `meta.json`, `vectors/`); `--out` must be gitignored or outside the repository. `npm run spec:check` proves it on the current text and on a fixture committed into a scratch repository, and needs the `hdtp-identity` checkout beside this one (or `HDTP_IDENTITY_DIR`). All licence wording is `site/licence.mjs`'s, read from `NOTICE`, `CITATION.cff`, the version line, `site/whitepaper.css` and `site/fonts.json`; never type it anywhere else. Every font a file names is an open font or a CSS generic family (`site/fonts.test.mjs`). Publishing is the maintainer's and local: `make publish` puts the PDF and its meta into the private bucket `hdtp-private`; `.github/workflows/whitepaper.yml` only checks and builds, and holds no credential.

`vectors/` is the other code: `gen.mjs` derives every key from a label (seeds `hdtp-1.0-vectors/{label}`) and writes `hdtp-1.0-vectors.json` — certificates to the §14.1 profile, chain cases per §14.2 rule, §14.3 comparisons, `certificate_renewed` cases, three `v: 1` envelopes (two full, one in the small form), the §2.1 derivations — reproducible byte for byte except ECDSA signatures; `check.mjs` reads the vectors *from the specification's Appendix B*, cross-checks every certificate with Node's OpenSSL-backed `X509Certificate`, and asserts each case's outcome and rule. `lib/` is the smallest implementation of §3, §13 and §14 that does that. `intrude.mjs` (`npm run vectors:intrude`) replays the §14.5 compromise cases and the corner cases around them against an in-memory node and reports blocked / residual-by-decision / REPRODUCES; a REPRODUCES is a spec finding, not a test to relax. Re-measure its count (`node vectors/intrude.mjs | tail -1`) before quoting it anywhere. It is the seed of the library, not the library — the library is the `hdtp-identity` repository, and the seed is its byte-level specification: a change here is a change there, proven by its `js/check.mjs` and `js/intrude.mjs` on both ports. Root private keys are deliberately absent from the vectors.

When implementing, treat all inbound strings from peers (text, notes, topics, filenames) as untrusted input to both UI and any LLM prompt — length-cap, never concatenate into instructions.
