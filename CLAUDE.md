# CLAUDE.md — project context for Claude Code

## What this project is

PACT: a protocol for person-to-person communication carried out by their AI assistant agents. Each person exposes an MCP server over HTTPS; contacts are mutual, human-approved, and pinned by TLS key fingerprint; messages, media, availability checks, and calendar booking are permission-gated MCP tools on that server. `SPEC.md` is the single source of truth. Everything in `docs/` and `archive/` predates the pivot and documents the **rejected** hardened design (its envelope variant with prekeys and delegations, DIDs, SAS, key transparency — the current, simpler envelope is SPEC §13, not the archive's) — `docs/landscape-and-roadmap.md` included: it never mentions vCard, `X-PACT-*`, or any current tool, and its §4 decisions, §5 build-vs-reuse, §6 roadmap and §8 section citations resolve only against `archive/hardened-draft-spec.md`. Never take a design decision, roadmap item, or cross-reference from either directory.

`explainer/pact-explainer.html` is an **Artifact body**, not a standalone page — it starts at `<title>` with no doctype/`<html>`/`<head>`/`<body>` wrapper; never add one. It is published at `claude.ai/code/artifact/6410d04a-ec41-45b5-bb97-fbc3801c4da1` — republish with that `url` or you create a second artifact.

## Design north star (decided, do not re-litigate without the owner)

- **Simple over hardened.** An earlier draft (archive/hardened-draft-spec.md) had E2E envelopes, key hierarchies, and verification ceremonies; the owner explicitly rejected that complexity. Security = plain mTLS with pinned SPKI fingerprints. **Partial, deliberate reversal (owner-directed, 2026-08-24):** the sealed envelope came back as SPEC §13 — HPKE Base + detached signature, same identity keypair, no DIDs, no SAS, no key hierarchies — because terminating edges and relays need identity and confidentiality that survive them. **Second reversal (owner-directed, 2026-09-12, the 2.0 generation):** an identity record came back in its smallest form — a person-held root, a scoped expiring grant to a host, a self-certifying log served under the endpoint (§14) — because an identity must be able to leave its host, and PACT Cloud is to be the first provider of a protocol nobody is locked into. Still no DIDs, no SAS, no prekeys, no directory, no recovery ceremony; a lost root is a new identity. The design of record is `pact-cloud/docs/superpowers/specs/2026-09-12-portable-identity-design.md` and the owner's overview page (artifact `b206b67a`). Do not reintroduce anything else from the hardened draft unless asked.
- **MCP-native.** Never invent a parallel message protocol; a capability is always an MCP tool behind the per-contact permission switchboard. Auth on this surface is transport-level mTLS, not OAuth.
- **vCard is the contact format.** `X-PACT-VERSION` (=2 in the 2.0 draft), `X-PACT-ID`, `X-PACT-HEAD`, `X-PACT-ENDPOINT`, `X-PACT-KEY`, `X-PACT-ENC`, `X-PACT-GATEWAY`, `X-PACT-SEAL`. Every value is 32-byte-key-sized so a card fits a QR code; the log's location is derived from the endpoint and never carried. Phone-book integration matters; no new sharing channels.
- **Invites are server-side state** (expiry, max_uses, auto_accept, preset, revocation) reachable via a short URL/QR. Nothing sensitive in the URL itself.
- **Honest trade-offs stay documented**: relays and edges see metadata (and read any unsealed traffic — sealed is ciphertext to them, SPEC §13); no forward secrecy at the envelope layer; lost key = new identity; card trust = channel trust. Keep these visible in docs and UX copy, never papered over.

## Spec conventions

- The current document is **v2.0.0-draft (2026-09-12)**: the identity generation on top of 1.2.0 (released 2026-08-30). It moves the card major to `X-PACT-VERSION:2` because the envelope header changed shape (`v: 2`, pids, `head`, `ekid`); Appendix C is the coexistence contract with 1.x and the compatibility card is the one place a 2.0 implementation writes `1`. The reference gateway implements 1.2 today; the identity log and verification library is the first sub-project of the 2.0 work and produces the §14 and `v: 2` vectors Appendix B still lacks. Wire-visible changes need a spec edit first.
- **Versioning policy (owner-set, 2026-08-30), X.Y.Z:** Z is the usual increment — ordinary edits, corrections, clarifications each release bumps Z. Y is a deliberate, significant release, bumped only when the owner says the accumulated work is ready to stand as one. X is a different story entirely — a wire-breaking protocol generation, and the only bump that moves the card's `X-PACT-VERSION` major. While a version is being worked on it carries a `-draft` suffix (`1.2.1-draft`); releasing drops the suffix, tags `vX.Y.Z`, and publishes the whitepaper: `npm run publish` uploads `dist/pact-whitepaper.pdf` AND `dist/pact-whitepaper.meta.json` to the private R2 bucket — the meta file is what pact-protocol.com/whitepaper/ reads to show the released version (injected server-side by pact-cloud's middleware; no site deploy needed). CI's Publish step does the same on every push to main — the repo secrets (`CLOUDFLARE_API_TOKEN` with R2 write on `pact-cloud-private`, `CLOUDFLARE_ACCOUNT_ID`, sourced from conductor's .env, set 2026-08-30) are live and verified, so pushing main IS publishing. `npm run publish` remains as the manual fallback. The whitepaper cover parses the spec's `**Version … · date …**` line, so that line is the single source of truth.
- Tool names snake_case (`send_message`, `redeem_invite`, `book_slot`); permissions dotted (`message.text`, `calendar.book`, `integration.<name>`); errors snake_case codes (`permission_denied`, `invite_invalid` — full list SPEC §12).
- Idempotency via caller-supplied `msg_id`; threads via shared `thread_id` + optional `topic`; `sender: agent|human` labeling is mandatory honesty.
- Guest tier (unknown certs) sees exactly `redeem_invite` + `request_contact`; `update_contact`, `remove_contact` and `get_card` are always available at contact tier regardless of permissions. Availability responses: ≤5 policy-filtered slots, never raw free/busy.
- The mermaid blocks all live in `SPEC.md`; keep them syntactically valid when editing — the whitepaper build renders every block and fails on one that does not parse. The explainer's diagrams are hand-authored inline SVG — this rule does not reach them.

## Owner's working preferences

Minimalistic, precise code that fits the module it lands in; read existing code first; no speculative features; stick to the objective. Prefer prose + small tables in docs over bullet sprawl.

The only build is the whitepaper: `npm ci && npm run build` (`site/build-whitepaper.mjs`) renders `SPEC.md` into `dist/pact-whitepaper.pdf` — markdown through `site/markdown.mjs`, mermaid to inline SVG and paged.js for page numbers, running headers and the contents page, all inside headless Chrome with the fonts and logo mark from `site/brand/` (nothing is fetched at build time). `.github/workflows/whitepaper.yml` builds it on every push to `main`, keeps it as a workflow artifact, and uploads it to the private R2 bucket when the Cloudflare secrets are set (`npm run publish` does the same locally). That build is the verification gate — it fails on headings over 120 characters, which is how an accidental setext heading (a paragraph followed directly by `---`) gets caught, and on any mermaid block that does not render. The cover's version and date are parsed from the spec's `**Version … · date …**` line; the spec's own "Table of contents" section is dropped in favour of the generated one. There are still no tests, linter, or runtime code; don't add them unless asked. `docs/` and `archive/` are deliberately not rendered. `archive/test-vectors/gen_vectors.py` is dead code for the rejected HPKE/SAS design and does not even import (`pyhpke` unavailable) — leave it.
