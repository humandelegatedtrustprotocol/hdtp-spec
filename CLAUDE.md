# CLAUDE.md — project context for Claude Code

## What this project is

PACT: a protocol for person-to-person communication carried out by their AI assistant agents. Each person exposes an MCP server over HTTPS; contacts are mutual, human-approved, and pinned by TLS key fingerprint; messages, media, availability checks, and calendar booking are permission-gated MCP tools on that server. `SPEC.md` is the single source of truth. Everything in `docs/` and `archive/` predates the pivot and documents the **rejected** hardened design (its envelope variant with prekeys and delegations, DIDs, SAS, key transparency — the current, simpler envelope is SPEC §13, not the archive's) — `docs/landscape-and-roadmap.md` included: it never mentions vCard, `X-PACT-*`, or any current tool, and its §4 decisions, §5 build-vs-reuse, §6 roadmap and §8 section citations resolve only against `archive/hardened-draft-spec.md`. Never take a design decision, roadmap item, or cross-reference from either directory.

## Design north star (decided, do not re-litigate without the owner)

- **Simple over hardened.** An earlier draft (archive/hardened-draft-spec.md) had E2E envelopes, key hierarchies, and verification ceremonies; the owner explicitly rejected that complexity. Security = plain mTLS with pinned SPKI fingerprints. **Partial, deliberate reversal (owner-directed, 2026-08-24):** the sealed envelope came back as SPEC §13 — HPKE Base + detached signature, same identity keypair, no DIDs, no SAS, no key hierarchies — because terminating edges and relays need identity and confidentiality that survive them. **Second reversal (owner-directed, 2026-09-12/13, the 2.0 generation):** a key hierarchy came back in its smallest form, and as X.509 rather than anything invented — **the person is a certificate authority**: a self-signed root in the person's wallet is the identity (pinned by its fingerprint), and the host holds a leaf the root issued, naming the endpoint in its SAN and expiring within 398 days (§2, §14). One leaf key does TLS, signatures and sealing. The certificate profile is exact (§14.1: nothing unlisted, strict DER). **Post-quantum is deferred by the owner (2026-09-13):** it was built and proven — X-Wing on Node's native ML-KEM, a `pactSealKey` extension, one hybrid suite `PACT-SEAL-XWING`, commit 77fd7ed — and reverted the same day; it returns with the pointer card and chain-once levers §13.5 records, so do not reintroduce it piecemeal. There is no log, no sequence number, no lineage, no relay (§9 is now *Hosting*): renewal is a new leaf learned from the chain every envelope carries, "newest `notBefore` wins the instant it is seen, no dampener" replaces revocation, a move is a new leaf for a new address plus `update_contact` from there under the receiver's `accept_new_hosts` setting (§5.3), and a host that is left deletes everything. Still no DIDs, no SAS, no prekeys, no directory, no recovery, and no root rotation; a lost or compromised root is a new identity. The design of record is `pact-cloud/docs/superpowers/specs/2026-09-12-portable-identity-design.md` and the owner's overview page (artifact `b206b67a`). Do not reintroduce anything else from the hardened draft unless asked.
- **MCP-native.** Never invent a parallel message protocol; a capability is always an MCP tool behind the per-contact permission switchboard. Auth on this surface is transport-level mTLS, not OAuth.
- **vCard is the contact format.** In the 2.0 draft: `X-PACT-VERSION` (=2), `X-PACT-CERT` (the leaf certificate, base64url DER — it carries the endpoint, the key, the root's fingerprint as issuer key identifier, and the validity), `X-PACT-SEAL`. The endpoint, key and gateway properties of the retired key-pinned generation are never written and never honoured (SPEC §3 names them). A card stays under a kilobyte so it fits a QR code; the invite URL carries print; a root is never in a card. Phone-book integration matters; no new sharing channels.
- **Invites are server-side state** (expiry, max_uses, auto_accept, preset, revocation) reachable via a short URL/QR. Nothing sensitive in the URL itself.
- **Honest trade-offs stay documented**: relays and edges see metadata (and read any unsealed traffic — sealed is ciphertext to them, SPEC §13); no forward secrecy at the envelope layer; lost key = new identity; card trust = channel trust. Keep these visible in docs and UX copy, never papered over.

## Spec conventions

- The current document is **v2.2.0 (2026-09-27)**: the identity generation, and the only generation — PACT 1.x support was removed entirely on 2026-09-17 (no `v: 1` envelopes, no key-pinned cards, no Appendix C, no relay role). `vectors/check-no-1x.mjs` fails `npm run vectors:check` if a 1.x name comes back anywhere but the SPEC's own refusal and the intrusion battery. It moves the card major to `X-PACT-VERSION:2` because the card's shape changed (one certificate instead of an endpoint and a key) and the envelope header lost `from`/`to` — `kid` names the recipient leaf key and the sender is inside the plaintext (`v: 2`, info `PACT-SEAL-v2`) — as `chain` on first contact and after a renewal, as `leaf`, a fingerprint, once the receiver holds the leaf, with `chain_required` answered uniformly when it does not — so carriers no longer see who sent a message and a "hi" stays small. the certificate and chain-validation library is the first sub-project of the 2.0 work — built 2026-09-14 as `pact-identity/` in the umbrella repository (a Rust core compiled to Wasm, an independent Go port and the `pact` CLI; the browser wallet lives in pact-cloud and is served, not installed), whose contract is `pact-identity/CONTRACT.md` and whose proofs run the same vectors and the same intrusion scenarios through both ports (`pact-identity/js/check.mjs`, `intrude.mjs --port wasm|go`). Appendix B carries the §14 and `v: 2` vectors, generated by `vectors/gen.mjs` and proven by `vectors/check.mjs` (see below). Wire-visible changes need a spec edit first, then `npm run vectors` and a re-splice of the JSON into Appendix B, then `npm run vectors:check`.
- **Versioning policy (owner-set, 2026-08-30), X.Y.Z:** Z is the usual increment — ordinary edits, corrections, clarifications each release bumps Z. Y is a deliberate, significant release, bumped only when the owner says the accumulated work is ready to stand as one. X is a different story entirely — a wire-breaking protocol generation, and the only bump that moves the card's `X-PACT-VERSION` major. While a version is being worked on it carries a `-draft` suffix (`1.2.1-draft`); releasing drops the suffix, tags `vX.Y.Z`, and publishes the whitepaper: `npm run publish` uploads `dist/pact-whitepaper.pdf` AND `dist/pact-whitepaper.meta.json` to the private R2 bucket — the meta file is what pact-protocol.com/whitepaper/ reads to show the released version (injected server-side by pact-cloud's middleware; no site deploy needed). CI's Publish step does the same on every push to main — the repo secrets (`CLOUDFLARE_API_TOKEN` with R2 write on `pact-cloud-private`, `CLOUDFLARE_ACCOUNT_ID`, sourced from conductor's .env, set 2026-08-30) are live and verified, so pushing main IS publishing. `npm run publish` remains as the manual fallback. The whitepaper cover parses the spec's `**Version … · date …**` line, so that line is the single source of truth.
- Tool names snake_case (`send_message`, `redeem_invite`, `book_slot`); permissions dotted (`message.text`, `calendar.book`, `integration.<name>`); errors snake_case codes (`permission_denied`, `invite_invalid` — full list SPEC §12).
- Idempotency via caller-supplied `msg_id`; threads via shared `thread_id` + optional `topic`; `sender: agent|human` labeling is mandatory honesty.
- Guest tier (unknown certs) sees exactly `redeem_invite` + `request_contact`, plus the every-tier wrapper `sealed_call` (when sealing is on); `update_contact`, `remove_contact` and `get_card` are always available at contact tier regardless of permissions. In 2.0 a pinned contact calling from a new endpoint is a *new address* (SPEC §5.3): re-pinned under `accept_new_hosts: auto`, pending under `ask`; a superseded leaf (older `notBefore` than the pinned one) is a guest. Availability responses: ≤5 policy-filtered slots, never raw free/busy.
- The mermaid blocks all live in `SPEC.md`; keep them syntactically valid when editing — the whitepaper build renders every block and fails on one that does not parse. The explainer's diagrams are hand-authored inline SVG — this rule does not reach them.

## Owner's working preferences

Minimalistic, precise code that fits the module it lands in; read existing code first; no speculative features; stick to the objective. Prefer prose + small tables in docs over bullet sprawl.

The only build is the whitepaper: `npm ci && npm run build` (`site/build-whitepaper.mjs`) renders `SPEC.md` into `dist/pact-whitepaper.pdf` — markdown through `site/markdown.mjs`, mermaid to inline SVG and paged.js for page numbers, running headers and the contents page, all inside headless Chrome with the fonts and logo mark from `site/brand/` (nothing is fetched at build time). `.github/workflows/whitepaper.yml` builds it on every push to `main` and keeps it as a workflow artifact; it holds no Cloudflare credential. Publishing is local and the owner's: `make publish` runs the gates and the build, refuses a PDF and meta from different builds, and puts both into the private R2 bucket that pact-protocol-site serves. That build is the verification gate — it fails on headings over 120 characters, which is how an accidental setext heading (a paragraph followed directly by `---`) gets caught, and on any mermaid block that does not render. The cover's version and date are parsed from the spec's `**Version … · date …**` line; the spec's own "Table of contents" section is dropped in favour of the generated one. The one other piece of code is `vectors/` (added 2026-09-13, owner-asked): `gen.mjs` derives every key from a label and writes `pact-2.0-vectors.json` — seven certificates to the §14.1 profile, chain cases per §14.2 rule, §14.3 comparisons, `certificate_renewed` cases, three `v: 2` envelopes (two full, one in the small form) — reproducible byte for byte except ECDSA signatures; `check.mjs` reads the vectors *from SPEC.md's Appendix B*, opens the four Go-generated `v: 1` vectors with the same HPKE code (the correctness anchor), cross-checks every certificate with Node's OpenSSL-backed `X509Certificate`, and asserts each case's outcome and rule. `lib/` is the smallest implementation of §13 and §14 that does that: strict DER, the exact X.509 profile and validator, HPKE Base for both suites with the Ed25519→X25519 maps, RFC 8785 canonicalisation, the §3 card codec, and an in-memory receiving node (`envelope.mjs`: §13.3 order, §6.1 tiers, §5.3 new addresses with the removal rule, §14.4). `intrude.mjs` (`npm run vectors:intrude`) replays the §14.5 compromise cases and the corner cases around them against that node — Mallory with a stolen leaf key, a stolen root and the war it starts, a former host's leaf, a squatted address, a guest naming the receiver's own address, tampered envelopes, replays, reused ephemerals, profile deviations, the ten DER misencodings the exact profile excludes, the small form's oracle and blocked-sender cases — and reports blocked / residual-by-decision / REPRODUCES; a REPRODUCES is a spec finding, not a test to relax. It stands at 95 scenarios, 91 blocked and 4 residual by decision (2026-09-15). It is the seed of the library, not the library — the library is `pact-identity/` in the umbrella repository, and the seed is its byte-level specification: a change here is a change there, proven by `pact-identity/js/check.mjs` and `intrude.mjs` on both ports. No tests, linter or other runtime code beyond `vectors/` here unless asked. Root private keys are deliberately absent from the vectors. `docs/` and `archive/` are deliberately not rendered. `archive/test-vectors/gen_vectors.py` is dead code for the rejected HPKE/SAS design and does not even import (`pyhpke` unavailable) — leave it.
